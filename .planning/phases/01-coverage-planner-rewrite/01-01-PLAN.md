<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GUI ↔ ROS2 (rosbridge) | Browser-supplied PlanCoverage.action goal crosses the GUI → ROS2 boundary; goal fields (start_pose, dock_pose, mow_angle_offset_deg, resume_from_checkpoint) are untrusted input |
| BT ↔ planner (WriteCheckpoint.srv) | BT-supplied Checkpoint payload is trusted (same DDS domain) but field values still need range-checking when written to filesystem |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | PlanCoverage.action goal from GUI | mitigate | Field validation in coverage_planner_node (Plan 05) — not in this interface plan; this plan only adds the schema. Out-of-range mow_angle_offset_deg, malformed Pose, etc. are caught downstream by the validator pipeline (SPEC R-12 ERROR_INTERNAL on field-validation failure). |
| T-01-02 | Information disclosure | PlanError.human_readable | accept | Operator-facing strings; no PII or credentials. Strings are constructed by planner from polygon indices, not from user input. Low risk. |
| T-01-03 | DoS | Spamming PlanCoverage goals | mitigate | rclcpp_action handle_goal rejects when planning_active_=true (RESEARCH §6.1). Implemented in Plan 05; this plan only ensures the action accepts/rejects flow is part of the schema. |
| T-01-04 | Tampering | WriteCheckpoint.srv from BT | mitigate | area_index range check + Pose finite-value check in planner service handler (Plan 05). This plan only defines the request shape. |

Severity: low/medium. No high-severity threat blocks this plan; this is a pure schema-definition plan.
</threat_model>
